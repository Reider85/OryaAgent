# ADR-0008: Tiered Model Routing — маршрутизация по сложности задачи

**Дата:** 2026-10-18
**Статус:** Proposed
**Связанные ADR:** ADR-0003 (tri-model), ADR-0015 (best-of-N)

## Контекст

Все 5 SOTA-агентов используют **одну** модель в сессии (пользователь выбирает через `/model`). Это значит:

- Тривиальные операции («прочитай файл и скажи, есть ли там класс Foo») выполняются большой дорогой моделью.
- Сложные задачи («отрефактори модуль с 20 файлами») выполняются той же моделью — но ей не хватает контекста или reasoning-глубины.
- Стоимость и latency определяются моделью, выбранной пользователем, а не сложностью задачи.

В архитектуре OryaAgent уже есть три фазы (ADR-0003): planner / executor / tester — каждая со своей моделью. Но внутри фазы executor'а тоже есть **разброс сложности**:

- «Поменяй константу с 5 на 10» — тривиально, можно на маленькой модели.
- «Реализуй новую фичу с нуля» — нужна большая.
- «Найди баг в concurrency-коде» — нужна самая большая (или best-of-N).

**Противоречие (ТРИЗ):** модель должна быть **дешёвой и быстрой** (для тривиальных задач), и модель должна быть **глубокой** (для сложных).

## Решение

Ввести **tiered model routing** — пул моделей трёх тиров + роутер, выбирающий тир по сложности.

### Тиры

| Tier | Примеры моделей | Latency | Cost / 1M tok | Назначение |
|---|---|---|---|---|
| **T0 — micro** | Qwen-3B, Haiku-3.5, 4o-mini, local-7B-q4 | 100–300 ms | $0.10–0.50 | Planner, tester, trivial edits |
| **T1 — mid** | Sonnet-4.5, GPT-5-mini, DeepSeek-V3, Qwen-32B | 1–3 s | $1–3 | Normal edits, refactors |
| **T2 — large** | Opus-4.5, GPT-5, DeepSeek-R1, Claude-Thinking | 3–15 s | $5–20 | Hard reasoning, complex features |

### Роутер

Роутер — отдельный маленький классификатор (на T0-модели или tiny BERT). Анализирует:

1. **Пометку planner'а** — planner уже классифицировал задачу (`trivial` / `normal` / `hard`).
2. **Метрики промпта** — длина, число файлов, наличие слов «refactor» / «design» / «debug» / «concurrency».
3. **Историю хода** — число replans, длительность предыдущих попыток.

На основе этого выдаёт tier для executor'а.

### Правила маршрутизации

- `trivial` → T0 сам исполняет (без отдельного executor'а). Один ход = planner (T0) → executor (T0) → tester (T0). Latency: <1 s.
- `normal` → planner (T0) → executor (T1) → tester (T0). Latency: 2–5 s.
- `hard` → planner (T0) → executor (T2) → tester (T1, mid — чтобы понять сложный код). Latency: 5–15 s. Опционально — best-of-N (ADR-0015).
- Если tester провалился 2 раза → эскалация на тир выше.

### Confidence-based fallback

Роутер выдаёт **confidence**. Если confidence < 0.6 — запуск на тир выше (страховка). Это плата за то, что классификатор может ошибиться.

### User override

Пользователь может явно зафиксировать тир через `/tier T2` (тогда роутер не выбирает — все ходы на T2). Полезно для «мне нужно максимальное качество, плевать на стоимость».

## Положительные последствия

- **Cost на типичную сессию падает в 3–10 раз.** 70% ходов — trivial/normal, идут на T0/T1.
- **Latency trivial-ходов <1 s** — модель не «тратит время» на тривиальные операции.
- **Quality hard-ходов растёт** — T2 там, где он реально нужен.
- **Adaptive** — система сама подстраивается под сложность задач пользователя.

## Отрицательные последствия

- **Риск недооценки сложности.** Роутер может отправить сложную задачу на T0 → tester провалит → replan → дороже, чем сразу на T1. Решение: confidence-based fallback + эскалация после 2 fail'ов.
- **Multi-provider сложность.** Нужны adapters для всех тиров на всех провайдерах. Решение: provider-seam (см. архитектуру).
- **Непривычно для пользователя.** Юзер не знает, какая модель сейчас работает. Решение: TUI показывает tier в реальном времени; `/tier` показывает текущий.

## Альтернативы

1. **Одна модель** (как SOTA). Отвергнуто: противоречие не разрешено.
2. **Ручной выбор модели пользователем на каждый ход.** Отвергнуто: UX-кошмар.
3. **Только T1 по умолчанию, эскалация на T2 после 2 fail'ов.** Рассматривалось; отвергнуто — теряем выигрыш на trivial-задачах.
4. **LLM-роутер (большая модель решает).** Отвергнуто: дорого; latency router-фазы превысит выигрыш.
5. **Машинное обучение на историю сессий.** Будущая оптимизация (ADR-TBD); в v0.1 — эвристики + confidence.

## Применённый ТРИЗ-принцип

- **Principle 35 — Parameter Change.** Меняем «концентрацию» модели под задачу.
- **Principle 1 — Segmentation.** Пул моделей сегментирован по тиру.
- **Principle 25 — Self-Service.** Роутер сам выбирает ресурс — не пользователь.
- **Principle 9 — Preliminary Anti-Action.** Confidence-based fallback — предварительная защита от ошибок роутинга.

## Идеальный финальный результат (IFR)

Стоимость хода пропорциональна сложности задачи, а не выбранной модели. Trivial-задачи — копейки, hard-задачи — достойное качество. Пользователь не думает о выборе модели — система делает это лучше него.
