# ADR-0001: Dynamic Fast Context — 4-уровневый контекст (HOT/WARM/COLD/ICE)

**Дата:** 2026-10-18
**Статус:** Proposed
**Связанные ADR:** ADR-0004 (prefetch), ADR-0007 (prompt-cache), ADR-0010 (compaction), ADR-0013 (diffs)

## Контекст

Все 5 рассмотренных в `analytics/agents-architect.md` архитектур (Claude Code, OpenCode, Kilo Code, DeepSeek Harness, MiMoCode) трактуют контекст как единый плоский массив `messages[]`. Рост проекта и длины сессии линейно увеличивает число токенов в окне, что прямо повышает:
- latency inference (O(N) для transformer attention);
- стоимость (провайдеры считают по input токенам);
- риск переполнения окна и аварийной компакции.

Попытки решения в SOTA:
- **OpenCode Context Epoch** — неизменяемый базовый префикс для prompt-cache; не решает объём.
- **MiMo checkpoint-writer + memory** — отдельная FTS5-память, но контекст сессии всё ещё в окне.
- **DeepSeek Harness sessionProjections** — проекционный шов, но модель всё равно видит весь лог.
- **Claude Code auto-compact** — реактивная компакция при переполнении, с потерей деталей.

**Фундаментальное противоречие (ТРИЗ):** контекст должен быть **большим** (модели нужны факты) и **маленьким** (большой = медленный и дорогой). Это физическое противоречие — к одному параметру (размеру контекста в окне) предъявляются взаимоисключающие требования.

## Решение

Ввести **четырёхуровневую память контекста**, в окно модели попадает только один уровень:

| Слой | Что хранит | Объём | Latency | Где |
|---|---|---|---|---|
| **HOT** | Символы/файлы, нужные в текущем ходу | 4–8 K tok | <1 ms | In-process LRU |
| **WARM** | Недавно использованные символы/файлы | 16–32 K tok | 1–5 ms | In-process LRU |
| **COLD** | Суммарные компакты предыдущих ходов | 32–64 K tok | 5–20 ms | RAM |
| **ICE** | LSP-индекс, embeddings, полный session-log | unbounded | 20–200 ms | Disk + LSP |

**HOT пересобирается на каждом ходу** на основе выводов planner-фазы (см. ADR-0003). WARM — это LRU-кэш для повторного использования без повторного retrieval. COLD — фоново обновляемые компакты (см. ADR-0010). ICE — структурированные индексы, доступные через retrieval-tools (см. ADR-0002, ADR-0005).

Модель в любой момент может вызвать retrieval-tool (`symbol.search`, `semantic.search` и т.д.), что эскалирует данные из ICE → HOT. Это не «галлюцинация в окне», а явный pull — модель знает, чего она не знает.

## Положительные последствия

- **Latency хода падает в 3–10 раз** на задачах с большим проектом: окно 8–24 K вместо 60–150 K.
- **Стоимость падает** пропорционально токенам в запросе.
- **Эффективный контекст не ограничен**: ICE растёт с проектом, окно — нет.
- **Prompt-cache работает на 80–95%**: cacheable prefix стабилен, HOT меняется только в хвосте (см. ADR-0007).
- **Predictable latency**: HOT-сборка детерминирована, нет «аварийной компакции» посреди хода.

## Отрицательные последствия

- **Сложность.** Четыре слоя + retrieval-tools + prefetcher + compactor — это существенно больше кода, чем «сообщения в массиве».
- **Риск ошибочного eviction.** Если prefetcher не догадался вытянуть нужный символ, модель сделает retrieval-call — это +1 LLM-итерация. На длинных задачах с непредсказуемыми зависимостями это может съесть выигрыш.
- **Нужна LSP-инфраструктура.** Без LSP (см. ADR-0002) ICE-уровень деградирует до grep+embeddings, что хуже.

## Альтернативы

1. **Long-context-only** (просто окно 1–2M токенов, как Gemini 2.0). Отвергнуто: стоимость и latency всё равно O(N); на 1M токенов один ход = десятки секунд даже у Gemini.
2. **RAG-only** (только retrieval, без слоёв). Отвергнуто: теряется «awareness» модели о том, что у неё есть; retrieval noise высокий; нет prompt-cache стабильности.
3. **Auto-compaction** (как Claude Code). Отвергнуто: реактивная, теряет детали; нет контроля над тем, что останется в окне.
4. **Memory DB** (как MiMo). Отвергнуто как единственное решение: хорошо для cross-session, не решает intra-session.

## Применённый ТРИЗ-принцип

- **Principle 17 — Another Dimension.** Контекст получает третье измерение: file × symbol × **time-of-relevance**. Слои HOT/WARM/COLD/ICE — это разделение по временной релевантности.
- **Principle 1 — Segmentation.** Один «контекст» сегментирован на четыре независимых хранилища с разными стратегиями.
- **Principle 15 — Dynamicity.** HOT пересобирается каждый ход; слои не статичны.

## Идеальный финальный результат (IFR)

Контекст существует весь, но в окне модели — только его минимальная актуальная проекция. Модель не чувствует границ контекста, потому что retrieval-tools работают быстрее, чем модель успевает сформулировать потребность.
