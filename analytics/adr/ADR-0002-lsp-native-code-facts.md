# ADR-0002: LSP-native code facts — LSP как первичный источник фактов о коде

**Дата:** 2026-10-18
**Статус:** Proposed
**Связанные ADR:** ADR-0001 (DFC), ADR-0005 (semantic index), ADR-0006 (parallel tools)

## Контекст

Все 5 SOTA-агентов добывают факты о коде через `read` (чтение файла целиком или постранично) и `grep`/`glob` (ripgrep-поиск). Это работает, но:

- **Дорого по токенам.** Чтобы понять сигнатуру функции, агент читает весь файл — 2–20 K токенов, чтобы получить 100–500 полезных.
- **Медленно.** ripgrep по большому проекту — 50–500 ms; LSP `workspace/symbol` — 1–5 ms.
- **Не точно.** grep по имени функции находит и комментариях, и в строках, и в других функциях с тем же именем. LSP `references` возвращает только реальные вызовы.
- **Не даёт типов.** Чтобы узнать тип аргумента, агент должен прочитать файл, найти определение, прочитать его тип. LSP `hover` возвращает тип мгновенно.

OpenCode и MiMo уже имеют LSP-клиент, но только для diagnostics. Никто из пяти не использует LSP как **первичный источник** структурированных фактов.

**Противоречие (ТРИЗ):** модель нуждается в **точных** фактах о коде (для отсутствия галлюцинаций), и факты должны быть **компактными** (для экономии токенов). Чтение файла даёт точность, но не компактность; grep даёт компактность, но не точность.

## Решение

Принять принцип: **любой факт о коде, который можно получить через LSP, не должен добываться через `read`/`grep`.**

Ввести **LSP bus** — менеджер LSP-серверов по языкам (gopls, rust-analyzer, pyright, typescript-language-server, jdtls, lua-language-server и т.д.). LSP bus:

1. Запускает LSP-серверы как child-процессы (stdio transport) при старте сессии.
2. Делает `initialize` с workspace root.
3. Подписывается на `textDocument/publishDiagnostics` → пушит в HOT-контекст.
4. Поддерживает `didOpen` / `didChange` / `didSave` через file watcher — индекс всегда свежий.
5. Экспонирует агенту retrieval-tools: `symbol.search`, `symbol.def`, `symbol.refs`, `symbol.hover`, `symbol.outline`.

LSP-сервер — это **полноправный intermediary** между файлами и моделью. Файлы остаются источником истины, но модель видит их через структурированный LSP-слой.

### Что LSP даёт «бесплатно»

| LSP-метод | Что заменяет в обычном агенте |
|---|---|
| `textDocument/hover` | `read(file)` + ручной поиск сигнатуры |
| `textDocument/definition` | `grep` + ручной анализ |
| `textDocument/references` | `grep` + ручной анализ вызовов |
| `textDocument/documentSymbol` | `read(file)` + ручной outline |
| `workspace/symbol` | `grep` по всему проекту |
| `textDocument/publishDiagnostics` | `bash(run linter)` — мгновенно вместо секунд |
| `textDocument/formatting` | `bash(run prettier)` |
| `textDocument/codeAction` | ручной refactoring |
| `textDocument/rename` | `edit` × N — один LSP-call делает безопасно |

## Положительные последствия

- **Token budget на факты о коде падает в 5–20 раз.** Сигнатура вместо файла — 100–500 токенов вместо 2–20 K.
- **Latency retrieval падает в 50–500 раз.** LSP `workspace/symbol` — 1–5 ms против 50–500 ms у ripgrep.
- **Точность.** LSP-сервер уже построил AST; мы не парсим заново. `references` возвращает только вызовы, не совпадения в строках/комментариях.
- **Безопасный refactor.** `textDocument/rename` делает rename через все references автоматически — без N отдельных `edit`-вызовов и риска пропустить.
- **Live diagnostics.** Diagnostics пушатся в HOT автоматически — модель видит ошибки сразу, без явного `bash(make)`.

## Отрицательные последствия

- **Зависимость от LSP-серверов.** Для малоизвестных языков LSP может не быть; fallback на grep+read обязателен.
- **Memory overhead.** LSP-серверы держат AST в RAM: gopls — 200–500 MB, rust-analyzer — 1–3 GB на больших проектах.
- **Startup time.** Холодный старт gopls/jdtls — 5–30 s. Решение: pre-warm при старте сессии, держать живым всю сессию.
- **Multi-language проекты.** Если в репо 4 языка — 4 LSP-сервера, 4× RAM. Решение: lazy-start по требованию.

## Альтернативы

1. **Только read + grep** (как Claude Code). Отвергнуто: точность, компактность, скорость — все три параметра хуже.
2. **Свой парсер на tree-sitter.** Отвергнуто: не даёт types/references без отдельного type-checker; дублирует работу LSP.
3. **SCIP/LSIF indexer** (Sourcegraph). Рассматривается как дополнение к LSP для очень больших проектов (см. ADR-0005), но не замена LSP — нет live-update.
4. **Embeddings-only.** Отвергнуто: хорошо для semantic, плохо для точных фактов (типы, refs).

## Применённый ТРИЗ-принцип

- **Principle 28 — Mechanics Substitution.** Заменяем «механическое» чтение файлов и парсинг их моделью на «информационное» поле LSP-сервера.
- **Principle 24 — Intermediary.** LSP-сервер — промежуточный объект между файловой системой и моделью, выполняющий работу, которую иначе делала бы сама модель.
- **Principle 10 — Preliminary Action.** LSP-сервер уже построил индекс до того, как модель сформировала запрос.

## Идеальный финальный результат (IFR)

Модель не читает файлы — она спрашивает LSP, и получает структурированный ответ. Файлы — это storage; LSP — это view. Модель работает с view.
